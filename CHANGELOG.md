# Changelog

## [Unreleased]

### Added
- **`surf pb record candidates` ranks a record's requests, and `--request-id` picks the one a draft replays** - Finding the request behind a page meant paging through `surf network` and `network.body`, and a draft took the last request it captured, a font on books.toscrape.com. `surf pb record candidates [<record-id>] [--limit n] [--json]` lists the record's requests best first, each with its `r_…` id, method, status, resource and MIME type, URL (query trimmed in text), size, a score with its reasons, and a short sample of the response. JSON and HTML documents, JSON holding a list of records, overlap with the page's visible text and the record's own site score up; telemetry, page assets, preflights, redirects without a body, tiny bodies and failed requests score down; writes are listed and flagged. Without an id it ranks your active record live (read from the tab), else the latest record your session or tab started. `pb record stop --draft --request-id <id>` and `pb save --from-record <id> --request-id <id>` replay the request you chose; a write still makes the draft a write, `--read` still refuses it, and telemetry, page assets and preflights are refused. `pb client derive --from-record` without `--request-id` now takes the top-ranked request when it clearly leads the next. To rank them, a record's trace keeps the structure of each response in place of its body: its kind, size, how many records a JSON body holds, how many top-level fields it has of each type, and how much of the page's text it contains. It keeps no values, text or field names (a key can be data, such as a username), from the response or the page. The response sample in the listing is shown only when ranking an active record, from memory, and is never saved; for a stopped record the listing shows the field counts instead.
- **`surf pb param` names a recorded op's inputs** - A recorded op replayed the exact request it captured, so `surf use books get_books --page 3` still fetched page 2, and naming an input meant hand-editing the op's JSON. `surf pb param <playbook> <op> <field>... --as <name>` puts `{{name}}` in each field and adds the input to the op, defaulting to the recorded value (`--required` or `--default <v>` to change that, `--desc <text>` to describe it). A field is `query.<param>`, a path inside a JSON-valued query param (`query.variables.page`), a path segment (`path.2`, with `--value 2` to template only that part, so `page-2.html` becomes `page-{{page}}.html`), a JSON, urlencoded or multipart body field (`body.slot_filter.party_size`) or a header. One input can fill several fields, and a workflow step that carries the same value (a `navigate` URL, typed text) takes it too, so the browser fallback follows. Surf prints a diff and saves the op in the scope it came from. It fails and says why when a field doesn't exist, the value isn't in it, the fields hold different values, or the name is already an input with another definition; running the same command again changes nothing. Values go into each place encoded for it: percent-encoded in the URL path and urlencoded bodies, typed in JSON, and a whole JSON query param sent as JSON. A string input keeps the text you pass, so `--id 2101.10010` isn't read as a number.
- **A header can come from an environment variable** - `surf pb param <playbook> <op> headers.<name> --env <VAR>` sends that header from the variable, for a site's public API key that Surf strips from recordings. `surf use` reads the variable from your shell and sends it with that one request (when your shell doesn't set it, the browser host's own environment is used); the value never reaches the playbook, the activity journal, a record, a receipt or a log, and a response or error that echoes it (as httpbin's `/headers` does) shows `<redacted>` in its place, in `surf use` output and in generated clients' output alike, wherever it appears, inside a longer word included; a value under 4 characters is replaced only where it stands alone, so it can't rewrite the data around it. An object key is a field's name, so it changes only when it is the whole value (4 characters or more) or holds one of 8 or more. A missing variable stops the run before anything is sent, naming the variable. Secret headers (`Authorization`, `Cookie`, API keys) take only `--env`, and a secret-looking field (or one inside a secret-looking param or key) takes only `--required` and is templated whole, without `--value`, so no value or part of one is stored.
- **Clients from ops with inputs take them as options** - `surf pb client export` of an op with inputs gives a `client.mjs` that takes the same `--<name>` options, with their defaults, required inputs and types, and fills the URL path, query, JSON and form bodies the way `surf use` does. Env headers are read from the client's own environment. `pb client verify` checks the filled request.
- **`surf pb extract` makes a playbook op return records instead of a raw response** - A recorded op that fetched an HTML page returned the whole page, and one that fetched JSON returned the site's full response, so every caller had to parse it again. `surf pb extract <playbook> <op> --item <css> --field name=<selector>[@attr] ...` saves the same item and field specs `surf collect` takes in the op, and `surf use` then returns one record per item: the network strategy parses the response body in the tab (relative links come back absolute), and a workflow strategy reads the same fields off the page it ends on, without `collect`'s visible tab. `--value <selector>[@attr]` reads one value instead, such as a form's hidden ID. For JSON, `--records '$.search.hits'` picks the array, `--field name=<path>` renames and selects fields (nested paths such as `venue.name` work), and `--filter path=value` keeps matching records, such as `__typename=Product`. It prints a diff of the op file and refuses a malformed selector or path before saving. Clients from `pb client derive` and `export` apply the JSON form without a browser, and `derive` takes it from the saved op. HTML extraction needs a DOM, so for an op that uses it they print a warning and the client returns the raw HTML. Both kinds of extract run in the tab and send back only their result, because what the tab sends back stops at 50,000 characters: a large response with a small extract works, and a result too large to send fails with `extracted result is N characters; narrow --records/--field` (or `--item/--field`). An op without an extract still gets the whole raw response, read from network capture (see Fixed).
- **`surf pb test` checks that a playbook op still works** - Checking an op meant running `surf use` and reading its output. `surf pb test <playbook> <op> [--<input> v | --args <json>] --assert <path> <op> [value] ...` runs the op the way `surf use` does and checks assertions: `equals`, `array_min_len`, `not_null`, `exists` and `matches`, on paths such as `$`, `$[0].title` or `$.status`. It prints a pass or fail for each assertion, which strategy answered, how many records came back and how long it took, and exits 1 when an assertion fails or no strategy answers (`--json` for the same as JSON). `--strategy network` runs one strategy alone, so a working network path can be told from a browser fallback. `--save` stores the assertions in the op once they pass; later `pb test` runs use them, and `surf use` checks them too, falling back to the next strategy when a read's result fails them. A write is never retried on another strategy: a failed check after it was sent leaves it in doubt. So a shared op can't hang the host, a `matches` pattern over 500 characters or that isn't a valid regex is refused wherever it comes from, and every run of a pattern is stopped after 100 ms and tests at most the first 64 KB of the text. A pattern stopped that way fails its assertion with `matches pattern took too long (over 100 ms); simplify it`, and `--save` refuses it. An op holds at most 50 assertions, and one op run spends at most 1 s on patterns in total; once that's spent, the remaining `matches` assertions fail with `skipped: the run's 1 s regex budget is spent` and `--save` refuses them. `pb test` refuses a write op without `--write`, and like `surf use` it rejects an input the op doesn't define, takes `--timeout` as the run's deadline and reads `pb param --env` headers from your shell. `--save` refuses an assertion whose path or value (any key or leaf) contains such a header's value, or whose `matches` pattern contains or matches it (broad patterns such as `.*` included), and any assertion the run marks as touching an env value (the browser host's own included, judged on the full value, not the 200-character preview), naming the assertion's position.

### Changed
- **`pb param --link` folds a drafted typed-value input into the named one** - A draft never stores a typed value, so its workflow types `{{text}}`, an input of its own, and `pb param` couldn't match it to the request field: the OrangeHRM and NCBI BLAST ops kept a stray required `--text` next to `--name` or `--sequence`. `surf pb param <playbook> <op> <field> --as <name> --link text` gives the workflow steps that take `{{text}}` the new input instead (loop bodies, `until` steps and nested loops included), and a `%{text}` a step reads from the op's inputs becomes `%{<name>}` (a loop's own var or a capture of that name is left alone, and a `<name>` a var can't take, one with `-` or `.`, is refused), drops `text`, and moves a write's safety key to `<name>`, so the op ends with only the inputs you named. Without `--link`, the note that the workflow is unchanged now names each workflow-only input and the `--link` to add. It refuses a `--link` input the op doesn't have, one a network strategy also uses, or one no workflow step takes, and it refuses, changing nothing, when a `%{text}` it would rename may read a capture or loop var named `text` or `<name>` instead of the input (a capture made in a loop or under `onError: continue`, a loop's own var, a capture of `<name>`), naming the step and the var; running it again changes nothing.
- **Fill and select results no longer repeat what was typed or chosen** - `locate.role`, `locate.text` and `locate.label` with `--action fill` print `OK` and keep the value out of the result, and `select` prints `Selected 2 options` instead of the option values, in the CLI, MCP and socket responses alike. Pass `--echo-value` to print them (`OK` then `Value: "…"`, or `Selected: a, b`), or set `"echoValue": true` in your own `~/surf.json` (a project's `surf.json` in the working folder can't turn it on). `type`, `smart_type`, `form_input`, `form.fill` and `select` also keep the value out of the page-change report (`value changed` instead of `value "" -> "…"`, and out of names and the navigated URL), and so do the results of these commands inside a playbook or `surf do` workflow, where a step can capture them with `as`; `--echo-value` shows them. `surf do --echo-value` (or `echoValue: true` in `~/surf.json`) shows them for a workflow's steps. A step can't opt in itself: the `echo-value`, `raw-bodies` and `include-input-values` arguments of a playbook step, a saved workflow's step (`surf do <name>` or `--file`, a project's `./.surf/workflows` included), a `--script` file's step (`surf --script` and `surf do --script`) and a `batch` action are ignored, since a project, an imported playbook or a file could set them.
- **Workflow results return only what their steps capture** - `surf use` on a workflow op and `surf do --json` returned every input they ran with under `vars`, so a password passed as an input came back in the output. `vars` now holds only the values steps captured with `as` (as `$.vars.<name>` extracts read them), including a capture that happens to equal a same-named input, and is left out when no step captures one. A step inside a `repeat` or `each` loop that fails under `onError: continue` no longer passes an input of the same name off as its capture.
- **A record redacts typed values in the URLs it captures** - A record without `--include-input-values` kept request bodies out of its trace but left a typed search term in `/api/search?q=…`, and from there in the draft's network strategy, saved and exported playbooks and `pb trace export --har`. A value that a `type`, `locate.* --action fill`, `form.fill`, `select` or other typing step entered during the record (from the command line, `surf do`, `--script`, `batch` or a playbook run with `surf use`), a `true` or `2024` the command line passes as a boolean or number included, now reads as a placeholder in captured request URLs, the page URL that sent them (`tabUrl`), `Referer` and `Location` headers, and the page URL of a `--watch` event. Only captured URLs are masked: a recorded `navigate` (`surf go <url>`) keeps the URL you gave it, typed values included and secret-named params such as `token=` aside, in the record's `events.jsonl`, the draft's workflow step and the saved op, so record a search through the page, or edit the step's URL in the saved op, when its URL holds a value you don't want saved. Surf splits each URL into its parts, decodes each part fully, compares typed values with the decoded text, and rebuilds the URL:
  - **Query values** (and a fragment's `?k=v` or `k=v`) are decoded the way forms are, `+` as a space, so a typed `foo+bar` doesn't match `?q=foo+bar` but `foo bar` does. `+` is a space only in a query or form value, at any depth: there, in the query values of a URL a value holds (`next=%2Fs%3Fq%3Dfoo%2Bbar`, however many times it is encoded), and in the values of `k=v` text decoded from a query value. It is never a space in a path, a key or a JSON string, so neither `{"q":"foo+bar"}` nor `next=%2Ffoo%2Bbar%3Fq%3Dx` holds a typed `foo bar`. A URL a value holds, absolute or relative (`/s?q=…`, `/s#q=…`, `#q=…`, `../s?q=…`, and a bare `s?q=…`), at any depth (in a query value, a fragment or a JSON string), is read exactly as the top-level URL is: split on its own `?`, `#`, `&` and `=` as written first, then each part decoded by its own rules, so an encoded `=`, `&`, `?` or `#` in a key or path never becomes a separator (`next=%2Fs%3Fq%253Dfoo%252Bbar%3Dsafe` sends the key `q=foo+bar`, not a typed `foo bar`), and its fragment reads by the top-level fragment's rules (`#/route=foo+bar` is a route, `#q=foo+bar` a form pair). A value is replaced when it is a typed value. A typed value of 4 or more characters is also replaced inside a longer value when no letter or digit touches it, so `pizza near me` gives `<text> near me`, while `name` inside `username` is left alone. Keys never change, and pairs with no typed value stay byte for byte as captured.
  - **JSON values** (a GraphQL GET's `variables={…}`) are read value by value, never their keys. Surf replaces string values as above. A string that is the typed value, even one that reads as JSON (`{"payload":"{\"q\":\"words\"}"}` for a typed `{"q":"words"}`), is replaced whole, and so is a string that still holds the typed value once decoded again (`{"q":"foo%20bar"}`, or `{"q":"foo bar, foo%20bar"}`). A string that holds JSON itself (`{"payload":"{\"year\":2024}"}`) is read the same way at any depth, its keys kept, as is JSON nested in arrays or objects any number of levels deep. A number, `true`, `false` or `null` is replaced when the typed value equals it as written (`2024.0`, `1e3`, `null`) or as read (`1000` for `1e3`). Only the replaced values change: every other byte of the JSON stays as captured, so its layout, escapes and large numbers (`9007199254740993`) are kept and it stays valid. A masked number or boolean becomes `"<text>"`, and the draft remembers its type (for one nested up to 32 levels deep; a deeper one gets no type, so the work stays linear in its depth), so `pb param query.variables.year --as year` makes `year` a number input and `surf use` sends `{"year":2031}`, not `"2031"`. A key that reads like an input is named as captured: for `v={"{{field}}":2024}`, `pb param 'query.v.{{field}}' --as year` makes a number input and sends the key as `{{field}}`. `pb param` reads the JSON as captured, so every other key and value goes out as captured too, one written with JSON escapes (`"\u007b\u007bx}}"`) included, and is never read as an input, while an input an earlier `pb param --value` put in the param's text (`v={"a":"{{a}}",…}`) stays an input when a field inside it is templated next, in a value or in a key (`--value seed-key` on `v={"seed-key":…}` sends `--key`'s value as the key, and keeps a masked number's type under it). A captured key that reads `{{key}}` beside it is still sent as captured, and `pb param 'query.v.{{key}}'` refuses to pick between the two. A key input whose value is a key already there (`--key n` beside `"n"`) is refused when the op runs, so no field is dropped. `surf use` and generated clients send a JSON param or body nested any number of levels deep, and `pb param`, `pb client export` and `pb client verify` read one as deep as an op file holds (Node writes the file to about 5,600 levels). A hand-written op's JSON text whose key takes an input stays text, since such an op sends an object's keys as written. The type is a note for `pb param`, never sent, so it never makes an input: a write saved network-only keys its duplicate guard on `review_key`, not on a `--text` the request never sends. When the URL sends the query key more than once (`v={…}&v={…}`), the draft keeps the key in its request URL with every value, masked, and remembers no type for it; a run refuses to send a masked value there, and `pb param` says the key can't be an input.
  - **Masking may guess; held may not.** Surf masks a value on any reading that could spell a typed value, but counts the value as sent (held), which keeps a path segment unmasked, only when a standard parser reads it there.
  - **Path segments** (and a `#/route`'s) are replaced only when the whole segment is the typed value and no query, fragment or request-body value certainly holds it. A value certainly holds it only as a site's parser reads it: each part decoded once by its own rules, a JSON string's value as written, and a URL split only on the `?`, `#`, `&` and `=` written at its own level, not on ones a further percent-decode produced, nor in a bare `s?q=…` or a `k=v` text. So `{"next":"/s%23q%3Dfoo%2Bbar"}`, or a double-encoded `next=%252Fs%253Fq…`, is masked as `<text>` and the route `/foo%20bar` beside it is masked too. `/api/users?q=users` keeps its route as `/api/users?q=<text>`, `/search/pizza` becomes `/search/<text>`, and `/search-users` is left alone. When two segments hold the value (`/users/users`), both are masked, since either could be the value. `pb param path.2` then says that `path.1` holds the same placeholder, and `pb param path.1 path.2 --as who` templates both with one input.
  - **Fragments** are replaced only when the whole fragment is a typed value (`#dummy/slash`).
  - **Other rules:** values under 3 characters are left alone. Each typing step gets its own placeholder, named like the draft's input for it: `<text>` and `{{text}}` for the first `type`, `<text-2>` for the second, `<value>` for a fill. Surf keeps a list of the placeholders it inserted, by position, so a later pass leaves them alone and still counts their values as held by the query. Each listed placeholder names the typing step's value it stands for, so a placeholder another value shares the name of (`<redacted>`, for values typed while paused) never counts that value as held. Text that merely looks like one, such as a typed `<text>`, is masked like any other value, and no character of the URL is ever taken for a placeholder.
  - **A check after each value:** once Surf has masked a query value, fragment or path segment, it decodes the result every way a site could (form and percent decoding, repeated, with a byte that isn't valid UTF-8 read as `�` the way `URLSearchParams` reads it; JSON strings and their escapes, at any depth). If any reading, at any depth and not only the last, still spells a typed value outside a placeholder Surf inserted or listed, or JSON the value held no longer parses, the whole value becomes one placeholder with no type. Surf finds its placeholders by position, so no character a page or a typed value can hold stands in for one, and page text that looks like a placeholder (`<redacted>` encoded five times) is read as any other text. A value with too many readings to check (one encoded a thousand times over) becomes `<redacted>` whole, and counts no typed value as sent, so a path segment holding one is still masked. Masking takes time near-linear in the URL's length (n log n, from finding placeholders by position), so a 112 KB JSON value, 8,000 masked numbers or JSON nested 4,000 levels under repeated keys take milliseconds.

  Surf holds the typed values in memory only while the record runs. If the browser host restarts during the record, `pb record stop` warns that values it no longer holds may remain. `pb param query.q --as q` on a masked field makes `q` a required input, since there is no recorded value to use as a default. It also hands the input to the typing step the placeholder came from and drops the draft's now unused input. An input counts as used only where the op fills or sends it: where `surf use` fills a request (its URL, header and query values and body, and in an op `pb save` escaped the keys inside them; never its `method`, `cache` or a `note`), a workflow's steps (a `{{name}}` anywhere in them, and a `%{name}` a step reads from the op's inputs: in a step's or `until` step's args, a loop's `repeat` or `each`, but not a loop's own item, `_index` or `_iteration`, nor a value an earlier step captured with `as`), an `api` or `collect` spec; a `script` or `native` strategy, which is given every input, keeps it. One only a check names (`verify`, `expect`, `extract`, `on.success.expect`), or a request field `surf use` never fills, is dropped, and a write's duplicate key moves to the new input, so `--text` can't key two writes that send the same request. A network strategy whose request still holds a placeholder is never sent. In a body, Surf counts a placeholder only when it is the whole body or a whole field value, so XML-RPC's `<value>` tag isn't mistaken for one. `surf use` skips such a strategy, names the `pb param` command that fixes it, and runs the next strategy; `pb client derive` and `export` refuse it the same way. `pb record start --include-input-values` keeps URLs as captured.
- **`network.export` redacts secret-named body fields** - JSON, JSONL and HAR exports (and `pb trace export --har`) kept request and response bodies such as `password=…` as captured. The values of secret-named fields (`password`, `token`, `api_key`, `session` and the other names recordings redact) now read `<redacted>` in JSON, urlencoded and multipart bodies, with the rest of the body kept; a text response Chrome sent as base64 is decoded, redacted and encoded again. `--raw-bodies` keeps bodies as captured. A playbook workflow step can no longer run `network.export`, whose bodies it would have returned unredacted. The private network store that `surf network` writes is not an export and is unchanged.
- **A draft replays the top-ranked request instead of the last one** - `pb record stop --draft` and `pb save --from-record` picked the last request the record captured, often a font, a script-loaded config or the page a redirect landed on. A draft now replays the request `pb record candidates` ranks first: never telemetry, page assets or preflights, and never a write on a read draft. A draft that is a write because of a request it captured replays its best write and never a read in its place; when it can't replay that write (a PUT, PATCH or DELETE), it gets no network strategy and a warning, and `--request-id` refuses a read for it. When the best request scores low, `pb record stop` warns and names `pb record candidates`. A trace with only telemetry, assets and preflights gives the draft no network strategy, with a warning.

### Fixed
- **`pb record candidates` ranks the page's own document above a banner JSON or the web manifest** - On arXiv, the search page's HTML held all of the page's text, yet `announcements.json` (a site banner listing 5 notices) and `site.webmanifest` scored the same 9 and the draft replayed the banner, with no warning. A response that holds 80% or more of the page's words now scores +5 instead of +3. A JSON body under 16 KB that holds under 10% of them is a side request when it lists no records, or when it is the web manifest or its path reads like a banner or announcements feed: it scores -3 (`small JSON that overlaps 1% of the page text`), and the feed's records don't count (`5 records not counted (the path reads like a banner or announcements feed)`). The path is only a guess, so when such a JSON would have beaten the pick with its records counted, `pb record stop --draft` warns, naming it and the score it would have had (on arXiv it names `announcements.json` and keeps the search page). So an arXiv search document that fits capture's 64 KB body cap scores 11 against the banner's and manifest's 3, and a 50-result page too large to sample (no overlap known) still scores 6 against 3. A JSON with records whose text isn't on the page, such as a chart's numbers, keeps its records bonus and still beats an empty app shell, and a JSON API that fills an app-shell page (crates.io's `/api/v1/crates`) still ranks first. When the draft's pick ties with the next request of the same kind or leads it by under 3 points (the margin `pb client derive` needs to take a request alone), `pb record stop --draft` warns, names both and points at `pb record candidates`. It also warns when it picks a document too large to compare with the page while a JSON with records was captured.
- **Generated clients take empty-string inputs** - `client.mjs` read `--author ""` as `true`, so an op with a `""` default (arXiv's optional search filters) sent `author=true`, and `pb client verify` failed on it. A client now reads `--name ""` and `--name=` as the empty string and `--name=value` as `value`; a bare `--name` is `true` only for an input the op declares a boolean, and for any other it fails with `--name needs a value (--name "" for an empty one)`. `pb client verify` now passes each sample value as `--name=value`, so a default that starts with `--` (`--submitted`) no longer fails with "needs a value". Clients exported before this fix still pass `pb client verify`: for them verify passes `--name value` and leaves out empty-string defaults, which the client fills in itself. Export again to run them with `--name ""`.
- **`network.get`, `network.curl`, verbose listings and the bodies `network.body`, `network.wait` and `network.replay` print no longer show secret headers** - `surf network.get <id>` (text and `--json`), `network.curl`, `network -v`/`-vv` and `network --format raw|curl` printed a captured request's `Authorization` header, cookies and API keys as captured, so reading a request (Resy's site key, on the recon) put the value in the terminal and the agent's transcript. They now show captured requests by the same rules as `network.export`: a secret header keeps its name with `<redacted>` as the value, secret-named query params and `user:password@` in URLs are redacted, and a body that echoes a secret header's value gets `<redacted>` in its place. The responses that `network.body`, `network.wait` and `network.replay` print (text and `--json`, and over MCP) hide such echoes too, in the body, its parsed JSON and the response's URL, so httpbin's `/headers` no longer shows the `Authorization` it was sent, nor an auth parameter's value (`api_key="…"`) or a cookie's value echoed alone, as written, JSON-escaped or URL-encoded; a response that is a secret's value whole (`[1]` or `{"x":1}`, however it is spaced) prints `"<redacted>"` as its JSON too, where `network.wait` and `network.replay` printed it parsed. A body `network.body` reads from Chrome when capture has no entry for it still prints, with no secret values known to hide. The replay itself still sends the real values, as do `surf use`, `collect` and recording, which read capture inside the host. There is no flag to print the raw value.
- **Field regexes and URL globs from an op file can't hang the host** - A `match` pattern on an `api` or `collect` field, or on a `pb extract` field, ran as a plain regex, so a shared op with one that backtracks (`(a+)+b` on a run of `a`s) could stall Surf for good; so could an `api` strategy's URL glob with many `**`. A field `match` is now refused when it is over 500 characters or isn't a valid regex, when an op is loaded or saved, as `matches` assertions are. On the host (and in a client from `pb client export`) each run is stopped after 100 ms and tests at most the first 64 KB of the text, and one op run spends at most 2 s on field patterns in total, across its fallback strategies, `collect` rounds and API pages, wherever they run: past either, the extract fails with `fields.<name>.match pattern took too long (over 100 ms); simplify it` or `skipped: the run's 2 s regex budget is spent`. In the tab (`collect`, HTML extracts and JSON extracts that run there) patterns never run on the page's own thread, where nothing could stop them: they run in a Web Worker that is stopped after 100 ms, with the same 64 KB limit, spending from the same 2 s. Surf runs them in a call of their own and charges at least the time it sees that call take, so a page can't make them cost less by rewriting what the tab reports or by making that call fail: a call that fails is charged all that was left of the 2 s, and one that took longer than what was left fails with the budget's error instead of giving its result. A script without patterns, such as a plain network request, costs the budget nothing. A page whose Content-Security-Policy blocks such workers sends the texts to Surf, which matches them on the host and finishes the extract in the tab without sending the request again; when the texts, as JSON, are too large for the tab's 50,000-character output, the extract fails and says to narrow the fields that use `match`. Every one of those lists is now checked when the op loads, and an op holds at most 50 assertions across all of them (`op get_books: at most 50 assertions per op across all its strategies and on.success (got 51)`).
- **`pb test --save` refuses a `matches` assertion when an env value is over 64 KB** - A pattern runs on at most the first 64 KB of a text, so it could match an env value longer than that without the check seeing it (`^(?:a{66000}z|ok)$` against a 66,001-character value), and `--save` stored it. With such a value, any `matches` assertion now counts as touching it: `--save` refuses it before the run when the value is in your shell (`the value of NAME is over 64 KB, too long to check assertion 1's pattern against`), and after it when only the browser host has it.
- **A failed assertion's error no longer records the value it found** - `assertion failed: $.note equals "expected" (got …)` quoted the response's value, which can be an op input echoed back, into the activity journal's `strategy.failed` events, write receipts and `surf use` errors. The error now names the assertion's path and op (`assertion failed: $.note equals`), plus why a `matches` pattern didn't run; `pb test` still shows each assertion's expected value and a redacted actual in its own report.
- **An env value that reads as a number is redacted where a response echoes it as one** - With an env header such as `123456789012`, a response holding `{"n":123456789012}` kept the number in `surf use` and `pb test` results, in `pb test --json`'s assertion values and actuals, and in generated clients' output (which masked it before `pb test` arrived). A number, boolean or `null` whose text holds an env value now becomes `"<redacted>"`, as a string holding it does.
- **A failed assertion no longer leaks an env value through its message or preview** - A failing `equals` on an env header's value put the value in its error JSON-quoted, so a value with a quote or backslash (`dummy"quoted\value`) slipped past redaction into the error, the run's attempts, `pb test --json` and the activity journal. And an actual value was cut to its 200-character preview before it was redacted, so a preview could keep the start of a value that began near its end. Each assertion's path, expected value and actual are now redacted in full before anything is built from them, the preview and the failure message included.
- **A playbook op's network strategy reads responses of any size** - The network strategy sent its request from the tab and returned the whole response through the tab script's output, which the extension cuts at 50,000 characters, so `surf use` on any response over about 50 KB (every books.toscrape.com catalogue page, a 460 KB Walmart search) failed with `Unterminated string in JSON at position 50000`. The script now reports only the status, URL and headers, and the body is read from network capture, as `network.replay` does; past capture's 64 KB per-body cap it comes from Chrome's own in-memory copy. Surf turns capture on before sending, and picks the captured request that is new, has the same URL and method, started while the script ran and has the status and headers the script saw. A redirected response counts only when capture shows the redirect chain starting at the op's own request, with the method each redirect gives it (a POST answered with 301, 302 or 303 becomes a GET; 307 and 308 keep the POST), so the page's own DELETE or GET of the same final URL is never taken for it; when capture can't show the chain, it fails (`POST /start was redirected to /final, and capture can't show which captured request it ended in, so surf won't guess`). When the page sent the same request itself meanwhile, it fails instead of guessing (`2 captured requests match GET /path while the op ran, and nothing tells which one it sent`), and when neither capture nor Chrome has the body it names the size and the cap (`it is 307215 bytes, over the 65536-byte per-body capture cap, and Chrome no longer has it`). An op with an HTML or JSON extract (`pb extract`) still runs it in the tab and doesn't read capture. Env-header values in the body are still redacted, a write is still sent once, and a write whose body can't be read is recorded as indeterminate.
- **Network exports no longer contain credentials** - `surf network.export` (JSON, JSONL and `--har`) and `pb trace export --har` copied every captured header and URL as is, so an export could hold an `Authorization` header (including one a playbook sent from an environment variable), cookies, API keys, or a token in a URL. Exports now keep secret headers' names with `<redacted>` as the value (the same headers recordings drop: `Authorization`, `Cookie`, `Set-Cookie`, API-key, CSRF, token and session headers), redact secret-named query params in `url` and `tabUrl` (and so in HAR's `queryString`), and drop `user:password@` from URLs. A text body that echoes a secret header's value (as httpbin's `/headers` does) gets `<redacted>` in its place; bodies are otherwise unchanged.
- **A failed `network.replay` hides short header values too** - Replay kept the page's header values out of its errors only when they were 8 characters or longer, so a short CSRF token or API key that the browser echoed in a fetch error was printed as is. Every header value is now replaced with `<redacted>`; one shorter than 8 characters is replaced where it stands alone, so the words around it stay readable.
- **`network.replay` says where to go when the tab has left the request's site** - Replay sends the request from the tab's current page, so after the tab moved to another site it failed with an opaque CORS error, or went out without the page's cookies. It now checks the tab first and refuses before sending, as in ``r_12 was sent from https://httpbin.org, but the tab is now on https://books.toscrape.com, so the browser would block it (CORS) or send it without its cookies. Run `surf go https://httpbin.org` first, then replay it.`` Replays from the request's own origin or the page that sent it work as before. A tab on a page with an opaque origin, such as `about:blank`, is always refused, as is a request sent from one, unless the tab is on the request's own origin. When the browser still refuses a cross-origin replay, the error names both origins.
- **`surf use` rejects inputs the op doesn't define** - `surf use <playbook> <op> --<name>` ignored any input the op didn't declare, so a typo such as `--lmit` ran the op with its default without a word. It now fails before anything runs, names the closest input when it looks like a typo, and lists the op's inputs, as in `Unknown input --bogus for page read. It takes no inputs`. `surf use`'s own flags (`--format`, `--json`, `--write`, `--allow-script`, `--repeat`, `--retry-attempt`, `--override-in-doubt`, `--pin-built-in`, `--timeout`) and Surf's global flags (`--session`, `--tab-id`, `--window-id`, `--no-wait`, `--no-diff`, `--settle` and the rest of `surf --help-full`'s options) are not inputs and still work; an op that declares one of those names still gets it.
- **A value typed with `locate.* --action fill` is no longer saved in clear** - `surf locate.role`, `locate.text` and `locate.label` with `--action fill --value <v>` wrote the value as typed to the activity journal, to a record's events and to drafts and playbooks saved from it, so a password filled this way landed on disk. The value is now redacted like the text of `type`, `form.fill` and the other typing commands, and a draft takes it as a `{{value}}` input instead of embedding it. When a dropdown has no option for the value, `locate.* --action fill`, `form_input`, `form.fill` and `select` no longer repeat the value in their error: it names the dropdown, how it matched and how many options it has, as in `e1 has no option matching the given value (by value or text, 2 options), so nothing was selected.`, and `select` with several values says which one failed by position (`given value 2 of 3`).
- **`pb record stop` saves the requests it captured** - Every record's network trace came out empty, so drafts never got a network strategy and `pb client derive` had nothing to use. Captured requests were dated by Chrome's own clock while the record's start was a normal date, and none compared as newer. Requests are now dated with the wall clock (`ts` in epoch milliseconds), which also fixes the request times in `network.export --har`.
- **A record only holds the commands of the session that started it** - One record took in every agent's commands and marks, from any session, and any session could mark or stop it. A record now belongs to the session that started it (or its tab, when started without a session). Other sessions' commands stay out of it, while the requests and page events on the record's tab are still captured, whoever causes them. Tab and window commands such as `tab.new`, `window.new` and `window.focus`, and `tab.unname` and `history.search`, go to the record of the caller's session (`--session` or `SURF_SESSION`, which they accept for this alone); without a session, such a command joins the only record that has no session. `mark`, `stop`, `pause`, `resume` and `discard` from another session fail and name the session that owns it, and each session can run its own record at the same time.
- **A record started before this update has no owning session** - Stop, mark or discard it from its tab without `--session` or `SURF_SESSION`.
- **`pb record stop --draft --read` drafts a search done by clicking as a read** - `pb record stop --draft` makes any record with a `click`, `type` or `key` a write, so `surf use` asked for `--review_key` to run a plain search. Pass `--read` to mark the draft a read. Surf refuses it, naming the request, when the record captured a request other than GET, HEAD or OPTIONS (beacons and analytics or error-reporting services aside, unless the record or the page is on that service's own site), when a step acts beyond the page (cookies, closing or naming tabs and windows, emulation, AI providers), or when the record ran without `--network`. With a gap in the capture (including requests cleared with `network.clear` during the record) it accepts `--read` and warns that not every request was checked. A POST that redirected, a POST answered with a script or stylesheet type, and a click or fill done with `locate.* --action` all count, and `network.replay --allow-post` makes a draft a write that `--read` refuses. Without `--read`, a captured request that can change data makes the draft a write too. A draft never replays telemetry, so a read never replays a POST.
- **Surf says when network capture stopped** - When the debugger detached from a tab (after a `back` that failed with `target_closed`, for example), Chrome stopped sending network events and Surf captured nothing more, without a word, so a record could miss the very request it was made for. Surf now notes when and why capture stopped, keeps the requests it already had, and turns capture back on before the next command on the tab, a `go` included, without that command first failing with `debugger_detached` (unless you cancelled debugging in Chrome; then the next command that needs the debugger does it). `pb record stop` returns a `warnings` line naming the gap (or saying capture wasn't running at all), and `surf network` ends with a `Warning:` line. A record with a gap no longer counts as proof that a click-and-type flow sent no writes.
- **`pb client derive` no longer turns a captured write into a read client** - `pb client derive --from-record` marked every client a read, even for a POST, PUT, PATCH or DELETE, so a captured create became a client Surf would export without review. A client derived from a request other than GET, HEAD or OPTIONS is now a write, and `derive` refuses it, POST reads included, for now.
- **`surf network --type json` and `--type html` find JSON and HTML responses** - `--type` compared its value with Chrome's resource type (`Document`, `XHR`, `Fetch`), so `--type json` and `--type html` always printed `No network requests captured`. It now matches the response's MIME type: `json` covers `application/json` and any `+json` type, `html` covers `text/html`, `proto` covers protobuf and gRPC, and a full or partial MIME type (`image/png`, `image/`) or a subtype (`css`) works too. Resource types (`document`, `xhr`, `fetch`) still work, in any case. `--type`, `--method` and `--status` now filter all captured requests before the list is cut to `--last` (100 by default), so older matches no longer drop out.
- **`surf network` shows request ids** - The `r_…` id that `network.get`, `network.body` and `network.replay` take was only printed with `--format raw` or `-v`. The listing (for example `surf network --last 20`; a bare `surf network` prints its help) now starts each line with it, and `surf network --json` puts the requests as JSON (`id`, `method`, `status`, `type`, `mimeType`, `url`) under `result.requests` in its usual `{result, target}` output, instead of the text table; `--format json` prints the same listing on its own.

## [2.26.0] - 2026-11-04

### Highlights
- When a click, typed text, dropdown choice or `locate` action doesn't work, Surf now fails and says why (`e5 is disabled`, `e2 is covered by dialog "Cookie consent"`) instead of printing `OK`. Clicks also wait for the element to be ready and use a real mouse click.
- `surf update` updates the CLI, the browser connection and the agent skill, then reloads the extension, all in one command. `surf install` no longer asks for an extension ID.
- `surf read` sees more of the page: form fields inside custom components, styled checkboxes, what each text field holds (never passwords), and a count of controls further down the page.
- New `surf check` and `surf uncheck` set a checkbox to the state you want, and `surf page.text --ref` prints a field's whole value.
- If you already use Surf, its extension ID changes once: rerun `surf install`, then reload Surf in `chrome://extensions`.

### Added
- **`surf check` and `surf uncheck` set a checkbox to the state you want** - Clicking a checkbox toggles it, so an agent had to read its state first or risk unticking a box that was already ticked by default. `surf check <ref>` and `surf uncheck <ref>` leave a checkbox, switch or radio alone when it is already in that state (`e6 was already checked; nothing clicked.`), and otherwise click it like a real mouse would, so pages that keep their own state in click handlers (such as React apps) see the change. If the control still isn't in the requested state after the click, the command fails. `uncheck` on a radio button fails and says to pick another option in its group. Thanks to [@morgan55555](https://github.com/morgan55555) for [#436](https://github.com/nicobailon/surf-cli/issues/436).
- **Surf can start your browser for you** - Set `"browser": { "autostart": true }` in `surf.json` and a command run while the browser (or its Surf host) isn't running starts it, waits up to 30 seconds for Surf to connect, then runs. `surf go <url>` opens the browser on that page instead of a blank new tab. Pick the browser with `"app"` (`chrome`, `chromium`, `brave`, `edge`, `arc` or `helium`) or give the exact command with `"command"`; `"timeoutMs"` changes the wait. Thanks to [@morgan55555](https://github.com/morgan55555) for [#424](https://github.com/nicobailon/surf-cli/issues/424).
- **`surf doctor` shows the CLI, native host and extension versions** - The CLI, native host and loaded extension come from one package but pick up a new version at different times, so they can run different versions. `surf doctor` now reports all three versions and fails with a `version-skew` check, naming the fix (`surf update`), when they differ.
- **Every command warns when the CLI, native host and extension versions differ** - The native host now sends its own version and the extension's with each response, and when either differs from the CLI's, the command prints one line on stderr, such as ``surf: version mismatch (cli 2.26.0, host 2.25.0, extension 2.25.0). Run `surf update`.`` The command's output and exit code stay the same, and a host too old to send its version prints no line.
- **`surf update` updates surf and reloads the extension in one step** - Updating used to mean reinstalling with npm, rerunning `surf install`, and clicking Reload in chrome://extensions, and a missed step left the CLI, native host and extension on different versions. `surf update` reinstalls with the npm that installed this surf (not whichever npm is first on PATH), or runs `npm ci && npm run build` in a linked repo checkout, refreshes the native host for the browsers that already have it and the agent skill links, asks the extension to reload itself, and prints the versions before and after (`--json` for `{before, after, steps}`). It changes nothing for an install it doesn't recognize. The first time, the running extension is too old to reload itself, so `surf update` asks you to reload it once in chrome://extensions.
- **`surf install` links the agent skill to the installed package** - The Surf skill for Claude Code and pi was copied by hand, so it fell behind the CLI. `surf install` now links `~/.claude/skills/surf` and `~/.pi/agent/skills/surf` to the `skills/surf` folder of the surf-cli you ran it with, so the skill updates with surf. It only links where that agent's skills folder already exists, repoints an existing link, and never touches a skill folder you made yourself: it says it kept it and that you can remove it and rerun `surf install` to switch. It skips pi when pi already loads surf-cli as a package, so the skill isn't loaded twice.
- **`surf install` no longer needs an extension ID** - Chrome gave each unpacked Surf an ID based on the folder it was loaded from, so you had to copy it from `chrome://extensions` into `surf install <extension-id>`. The extension now carries a fixed public key, so every Surf build has the ID `oaclimdkkglbnpekeignmjenkodkaaka`. `surf install <extension-id>` still works for a fork or a build with a different ID. If you already use Surf, its extension ID changes once: rerun `surf install`, then reload Surf in `chrome://extensions`. Until you reload, the old copy keeps working; afterwards a disabled copy under the old ID stays listed until the browser restarts. Settings the old extension stored, such as Debug Mode, don't carry over to the new ID.
- **`surf page.text --ref` prints one field's whole value or one element's text** - To check a long note or cover letter before sending it, you had only `surf read`, which cuts a field's value at 80 characters and joins its lines, or a `surf js` call with a CSS selector. `surf page.text --ref <ref>` now prints a text field's, textarea's or editable area's whole current value, newlines included, and any other element's rendered text. A secret field (the same ones `read` shows as `[value hidden]`) fails with `e4 is a secret field, so its value is not shown` and its value is never sent. Thanks to [@morgan55555](https://github.com/morgan55555) for [#449](https://github.com/nicobailon/surf-cli/issues/449).
- **`surf type --escapes` types newlines and tabs** - Putting a real newline or tab into a shell argument is awkward, and smaller models often can't, so `surf type "line1\nline2"` typed a backslash and an `n`. With `--escapes`, `\n`, `\t`, `\r` and `\\` in the text become a newline, tab, carriage return and one backslash before typing, on every `type` path (`--ref`, `--into` and at the cursor). Any other backslash sequence is typed as written. Without the flag, `surf type` types the text literally as before. Thanks to [@morgan55555](https://github.com/morgan55555) for [#451](https://github.com/nicobailon/surf-cli/issues/451).

### Fixed
- **`surf read` says how many controls it left out for being off-screen** - `surf read` lists only the controls on screen unless you pass `--all`, and gave no sign that more were further down the page, so agents read a page, missed the controls below the fold, and sometimes decided the page was broken. When controls are left out for being off-screen, `surf read` now ends with a line such as `+142 elements off-screen: surf read --all`. There's no such line when nothing was left out, or with `--all` or `--ref`. Thanks to [@morgan55555](https://github.com/morgan55555) for [#452](https://github.com/nicobailon/surf-cli/issues/452).
- **`locate` no longer acts on the wrong element** - `surf locate.role`, `locate.text` and `locate.label` with `--action` used to act on the first element whose name contained your words, and printed `OK`, so `surf locate.role button --name "Save" --action click` could click "Save draft", and `--name "Delete"` on a list clicked the first row's Delete button. Now an element whose name is exactly what you asked for wins over partial matches, and when more than one element still matches, nothing is clicked or filled: the command fails and lists each match with its ref, so you can act on the one you mean with `surf click <ref>`.
- **Typing into a field that can't take the text fails instead of saying OK** - `surf type "<text>" --ref <ref>`, `surf type "<text>" --into <selector>` and `surf form.fill` used to write past a field's character limit, overwrite a read-only field, and print `OK` when the page threw the text away. Now a read-only or disabled field, or text longer than the field allows, fails with the reason, such as `e1 accepts at most 4 characters, but 8 were given`, and nothing is written. If the field still holds its old value after typing, or the page empties it, the command fails with `did not keep the typed text`. A field that reformats what you typed, such as a phone number mask, still counts as success. A `form.fill` that fills some fields but not others now fails too, says how many it filled, and names each field it couldn't fill.
- **Errors say what went wrong instead of "Try refreshing the page"** - When a page command such as `read`, `click`, `type`, `locate.*` or `wait.element` failed for any reason, Surf said `Content script not loaded. Try refreshing the page.`, even when Surf was working on the page and something else went wrong. Refreshing then threw away what was typed into the page. Surf now says this only when its script really isn't answering on the page. A command cut short because the page navigated or closed says so, and any other failure shows its real error.
- **Clicking by ref only clicks what a user could click** - `surf click <ref>` and `surf locate.* --action click` used to fire the element directly and print `OK` for a disabled button, click straight through a cookie banner or dialog covering it, and do nothing on buttons that ignore script-made clicks. Now Surf waits up to 5 seconds for the element to be visible, enabled and not covered, scrolling it into view if it is hidden inside a scroll box, then clicks it with a real mouse event. If it never becomes clickable, the command fails with the reason, such as `e5 is disabled` or `e2 is covered by dialog "Cookie consent"`, and nothing is clicked.
- **A ref from an earlier page no longer clicks something on the current one** - Every page used to number its elements from `e1`, so after a navigation or reload an old ref such as `e2` named a different element on the new page, and `surf click e2` acted on it and printed `OK`. Within a tab, a new page now numbers its elements after the ones earlier pages used, so refs never repeat. Using a ref from an earlier page fails and names that page, such as `e2 is from an earlier page in this tab (https://example.com/plan). Run surf read to get current refs.` A page you go back to from the browser's back/forward cache keeps its own refs.
- **Custom buttons, links, tabs and menu items show their names** - A control built from a `<div>` or `<span>` with a role such as `button`, `link`, `tab`, `menuitem` or `option` got an empty name when its text sat inside a child element or was shorter than 3 characters, so `surf read` listed `<div role="button"><span>Save</span></div>` as `button ""`, and `surf locate.role button --name "Save" --action click` refused because it couldn't tell such buttons apart. These controls now take their name from their text, as `<button>` already did, so `surf read` shows `button "Save"` and `locate` picks the exact one. Table cells and headers are named from their text too. See [#430](https://github.com/nicobailon/surf-cli/issues/430).
- **A click that can't be a real mouse click says so** - When `surf click <ref>` or `locate.* --action click` couldn't send a real mouse click, it fell back to clicking the element inside the page and still printed only `OK`, so you couldn't tell why a site ignored it. Now the output adds a line such as `Clicked e3 inside the page, not with the mouse, because its tab is hidden (a background tab, or a window behind other windows). If nothing happened, switch to the tab (surf tab.switch <id>) or bring its window to the front and retry.` Clicks in hidden tabs, inside frames, or when Surf can't attach its debugger still go in the page after the same checks, and now say why. After you click Cancel on Chrome's "is debugging this browser" bar, the next ref click attaches again and sends a real mouse click instead of quietly falling back.
- **Form fields inside custom components are now visible** - Pages that build their forms from custom elements with open shadow roots, such as job application forms on SmartRecruiters, showed none of their fields in `surf read`, and `surf locate.label "First name"` found nothing. Surf now reads through open shadow roots, so those fields and buttons appear with their names (taken from the label inside the component), you can click and type into them by ref as usual, and `locate.label`, `locate.role` and `locate.text` find them too, acting on the field inside the component rather than on the component that shares its id. Closed shadow roots stay unreachable. Thanks to [@morgan55555](https://github.com/morgan55555) for [#437](https://github.com/nicobailon/surf-cli/issues/437).
- **Selecting an option that doesn't exist fails instead of saying OK** - `surf select <ref> <value>` printed a warning but exited 0 when no option matched, and `surf form.fill` quietly emptied a dropdown it couldn't match. Both now fail and change nothing, for example `e5 has no option matching "nowhere" (by value), so nothing was selected.` `form.fill` matches a dropdown option by its value or its visible text.
- **`read` shows what a field holds, and never a password** - `surf read` listed a text field by its label or placeholder but not its contents, so checking what `surf type` or the user entered took a `surf js` call. Text inputs, textareas and editable areas now show their current value, such as `textbox "hello@example.com" [e85] type="email" placeholder="hello@example.com" value="hello22"`, cut at 80 characters with `...`. Secret fields show `[value hidden]` instead: `type="password"` fields, fields whose `autocomplete` is `current-password`, `new-password`, `one-time-code` or a `cc-` card token, and fields the page masks on screen with `-webkit-text-security`. The page-change report after `surf type` now hides masked fields' values too. `read` also no longer prints a password as the field's name: a password field Surf couldn't otherwise name, such as one inside a `<label>` without `for`, used to appear as `textbox "<the password>"`. Thanks to [@morgan55555](https://github.com/morgan55555) for [#434](https://github.com/nicobailon/surf-cli/issues/434).
- **On Android, `surf doctor` says why it can't work and what to do instead** - In Termux, `surf doctor` and a failed command told you to make sure the browser was running with the Surf extension, but no Android browser can run the extension's native host. Now `surf doctor` fails with that reason and both point to running the browser on a desktop machine and connecting with `surf --remote <host>:<port> --remote-credential <file>`. Thanks to [@shankarkrupa](https://github.com/shankarkrupa) for [#417](https://github.com/nicobailon/surf-cli/issues/417).
- **`surf install` sets up the host from the surf you ran it with** - With two surf-cli installs on PATH (for example one from a Node version manager and one from Homebrew), `surf install` pointed the browser's native host at whichever copy `npm root -g` named, so the browser could run a different, older host than your `surf` command. It now always uses the host from the same install as the `surf` you ran. `SURF_HOST_PATH` still overrides it.
- **Page text no longer fills up with CSS rules** - `surf page.text` and the `--- Page Text ---` part of `surf read` took every bit of text in the page's markup, so on sites that put their styles and scripts inside the page body (such as Tilda sites) the output was mostly CSS and JavaScript. They now return the text the page actually shows. Styles, scripts and hidden content such as collapsed sections or `display:none` blocks are left out. Thanks to [@morgan55555](https://github.com/morgan55555) for [#435](https://github.com/nicobailon/surf-cli/issues/435).
- **`page.html` and `page.save` work without `--selector`** - `surf page.html` and `surf page.save --output <file>` failed with `Value is unserializable` unless you passed `--selector`, because Chrome refuses an empty argument in the script it runs. They now return the whole document with its `<!doctype>` line. Thanks to [@doctorguile](https://github.com/doctorguile) for [#423](https://github.com/nicobailon/surf-cli/issues/423).
- **`surf read` lists form fields the page draws over with a transparent input** - Styled checkboxes, radios and other fields often leave the real `<input>` at `opacity: 0` and draw their own box beneath it, so `surf read` left the field out unless you passed `--include-hidden`, and `surf check` or `surf click` on it reported `no visible change`. Now an `input`, `select` or `textarea` that is transparent but otherwise shown appears in `surf read` and its YAML output, `surf check` reports its change (`e3 checkbox "I agree"  now checked`), and an old ref to it still finds it after the page re-renders. Other transparent elements, such as faded-out menus and buttons, stay hidden. Thanks to [@morgan55555](https://github.com/morgan55555) for [#450](https://github.com/nicobailon/surf-cli/issues/450).

### Highlights

Cloudflare's Clef now works too, with your own Cloudflare account, and with `--vision` it finds icon-only buttons: the right icon in 30 of 30 test runs, against 0 of 30 without it.

Cloudflare's Clairic finds each value by meaning and returns it as a real number or date, or `null` when it isn't on the page. `surf do` workflows can read and check these values too.

### Added
- **Choose the semantic model** - `semantic.find`, `semantic.filter`, `semantic.verify` and `semantic.act` take `--model jev-1.13.0|clef|clef-flash`. `SURF_SEMANTIC_MODEL` sets the default, and it is the only way to pick the model for semantic `surf do` steps. With nothing set, Surf uses `jev-1.13.0` as before. Page text goes to the provider of the selected model: TypeSafe (`api.typesafe.ai`) for Jev, Cloudflare Workers AI (`api.cloudflare.com`) for Clef. Each model has its own confidence thresholds; [docs/semantic-models.md](docs/semantic-models.md) lists them and compares the models on accuracy and speed. Clef is less sure than Jev of answers it gets right, so `clef` clicks and fills from 0.85 instead of Jev's 0.95, and needs 0.70 instead of 0.75 when it judges whether the goal can be done on the page. That lets it click right answers it used to refuse, such as the menu button on DuckDuckGo's settings page, with no wrong click or fill in testing. On busy pages such as an X post, Clef still picks the right button but stays below 0.85, so it stops there. `jev-1.13.0` and `clef-flash` keep 0.95 and 0.75. See [#354](https://github.com/nicobailon/surf-cli/issues/354) and [#392](https://github.com/nicobailon/surf-cli/issues/392).
- **Icon-only controls with `--vision`** - `semantic.find` and `semantic.act` take `--vision` with `clef` or `clef-flash`. The model then also gets one small image of the controls that have no name, such as icon-only buttons, each tagged with its ref, so "the download icon" no longer has to be guessed from identical `button` entries. Each tile is drawn from the control's own icon on a blank canvas. No screenshot of the page is taken or sent, so field contents and anything else on the page can't appear in it. Icons Surf can't draw, such as canvas drawings, CSS gradients or controls inside frames, are left out and counted as skipped, and nothing extra is sent on a fully labeled page. Results report `vision: { tiles, skipped }` and mark a returned candidate or action that was shown as a tile with `"tile": true`. `--allow-write` and `--allow-ref` work as before. With Jev, `--vision` fails before anything is sent. If the tiles can't be built, the command fails with `semantic vision failed: <cause>` instead of answering from text alone. On a test toolbar, `semantic.find` picked the right icon in 30 of 30 runs with `--vision` and 0 of 30 without, on both Clef models; it also lowered confidence on a labeled button, so use it for icon targets. Details are in [docs/semantic-models.md](docs/semantic-models.md#icon-only-controls---vision). See [#355](https://github.com/nicobailon/surf-cli/issues/355).
- **Cloudflare credentials** - Set `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN`, or run `surf semantic auth set --provider cloudflare`. It asks for the account id, then the token without echoing it, and saves them in a private file, `~/.config/surf/cloudflare-credentials.json` (`%APPDATA%\surf\cloudflare-credentials.json` on Windows), separate from the TypeSafe key. If Clef has no credentials, the error tells you exactly what to set or run. `surf semantic auth status` and `clear` cover both providers unless you pass `--provider`. Status shows only where each credential comes from and a short fingerprint.
- **Run summary** - Every semantic result, including runs stopped by a budget or a failed decision, reports `provider`, `model`, `providerCalls` and `providerLatencyMs` (the total provider round-trip time). When a command fails, the summary is printed on stderr after the error. Semantic `surf do` step results report the same fields in their `semantic` block.
- **X thread playbook** - `surf use x thread --url <post-url>` returns the thread author's posts in order: id, author, name, time (ISO 8601, UTC), full text of long posts, images, the quoted post, and a link. It reads X's own TweetDetail response and falls back to scrolling the page. Add `--format md` for Markdown or `--format jsonl` for one post per line.
- **`network.wait`** - Waits for the page's next response whose URL matches a glob such as `/api/*/feed` and prints its JSON. With `--open <url>`, capture starts before the page loads. If nothing matches, the error lists the API paths it did see.
- **`network.replay`** - Re-sends a captured request from inside its tab with edits such as `--set query.cursor=abc` or `--set query.variables.cursor=abc` (a field inside a JSON query param), and prints the response. Only GET and HEAD are re-sent unless you pass `--allow-post`. Request header values never appear in its output or errors.
- **`collect`** - Scrolls a list, including virtualized lists that keep only a few items on the page, and returns one record per item, deduped by key: `surf collect --item article --key 'a@href' --field title=h2`. It needs a visible tab and fails in a background tab.
- **`api` and `collect` playbook strategies** - Playbooks can map the site's own JSON responses to records, turn date fields into ISO 8601 UTC with `"as": "datetime"`, and follow its pagination cursor, or scroll and collect items from the page. `surf use <playbook> <op> --format md|jsonl` prints the records as Markdown or JSON lines. How to write a recipe, with a working Bluesky example, is in [docs/threads-and-feeds.md](docs/threads-and-feeds.md).
- **Upload through the upload button** - `surf upload --ref` now also takes the ref of the button that opens the file picker, not just the `input[type=file]`. Surf clicks the button, answers the file chooser it opens, and sets the files on the input Chrome names, so pages that keep the input hidden or outside the dialog (such as LinkedIn Easy Apply) work. If no file chooser opens within 10 seconds, the command fails and says so. Thanks to [@morgan55555](https://github.com/morgan55555) for [#363](https://github.com/nicobailon/surf-cli/issues/363).
- **Read values off a page with `semantic.extract`** - Ask for named, typed values instead of reading the whole page: `surf semantic.extract --field total:number:"Order total" --field delivered:date`. The types are `text`, `number`, `integer`, `date`, `time`, `datetime`, `duration` (with a unit such as `duration.minutes`), `list`, `list.number` and `list.date`; `--fields-json` adds units, decimals and a per-field null threshold. Each value reports its `confidence`. A value that isn't on the page comes back `null`, and one below the confidence threshold is withheld and reported as `guess`. A text value names the page text chunk or control ref it came from when Surf can match it exactly. It runs on Cloudflare's Clairic extraction model (a preview) with the same Cloudflare credentials as Clef, and sends Cloudflare the same page text that Clef gets. How its threshold was measured is in [docs/semantic-models.md](docs/semantic-models.md#extraction-clairic). See [#385](https://github.com/nicobailon/surf-cli/issues/385).
- **Read and check values in a workflow with `extract` and a value assert** - A semantic `surf do` workflow can read typed values off the page with `{"op":"extract","fields":{...}}` and an `as` name. `fields` uses the same grammar as `semantic.extract --fields-json`. The step makes one Clairic call, which counts against the workflow's `maxProviderCalls`, and needs Cloudflare credentials but no TypeSafe key unless the workflow also has decision steps. The result shows up as `vars.<as>` in `surf do --json` output, and step results report Clairic's totals under `semantic.extraction`. Extracted values are never written to the workflow's state files. A later `{"op":"assert","mode":"value","binding":"order","field":"total","equals":42.1}` step checks one field against a literal, an `input` slot (`--expectedTotal 42.10` or `--inputs-stdin`), or an inclusive `min`/`max`, with numbers rounded to the field's `decimals`. A `null` or `uncertain` field always fails it, even when its `guess` matches, and its failure message is only a reason code (`value_null`, `value_uncertain`, `assertion_mismatch`), never a value. See [#387](https://github.com/nicobailon/surf-cli/issues/387).

- **Semantic locators** - `locate.role`, `locate.text`, `locate.label` commands to find elements by ARIA role, text content, or label. Supports `--action click|fill|hover|text` to act on found elements.
